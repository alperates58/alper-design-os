# Alper Design OS — Operator-Assisted Execution Hotfix (Phase 1E.7.1)

## 1. Context & Motivation

In hardened enterprise and corporate desktop environments, background AI agent processes (such as Antigravity runner subprocesses) are often subjected to Endpoint Detection and Response (EDR) sandboxing (e.g. Xcitium / Comodo Security). Under these restrictions, the automated agent process may receive `Erişim engellendi` (Access Denied / blocked process spawning) when attempting to directly invoke executables like `cmd.exe`, `node.exe`, or `docker.exe`.

However, the **authenticated human developer / operator** logged into the Windows session possesses full execution rights to run:
- Docker Engine & Docker Compose
- Node.js & pnpm
- Playwright testing
- Microsoft Edge & Google Chrome

**Core Principle:**  
Runtime verification should **never be blindly deferred to a home computer** simply because the agent's sandboxed child-process runner encountered corporate process restrictions. The human operator is a first-class collaborator in the execution pipeline.

---

## 2. Execution Modes Taxonomy

Alper Design OS defines 4 distinct execution modes:

| Execution Mode | Description | Used When |
|---|---|---|
| `DIRECT_AGENT_EXECUTION` | Agent directly executes commands in the local shell. | Local environment has zero sandbox or process restrictions. |
| `HUMAN_OPERATOR_EXECUTION` | Agent prepares an execution bundle; human runs it in standard PowerShell; agent audits evidence. | Corporate workstation where agent child-processes are restricted by security policy. |
| `CI_EXECUTION` | Automated non-interactive continuous integration runner. | Cloud/headless pipeline runners with service tokens. |
| `UNAVAILABLE` | Neither agent nor operator can execute the required capability. | Required dependencies (e.g. Docker or Node) are genuinely absent from the system. |

## 3. Manual Run Bundle Architecture

When runtime verification is required in `HUMAN_OPERATOR_EXECUTION` mode, Alper Design OS automatically generates an execution bundle at:

```
.alper-design-os/manual-runs/<run-id>/
├── RUN.ps1                 # Standalone PowerShell script for the human operator
├── README.md               # Clear operator instructions and objective
├── expected-evidence.json  # Manifest of mandatory evidence artifacts
└── evidence/               # Target directory populated during execution
```

### Automatic Evidence Generation
Executing `.\RUN.ps1` in standard Windows PowerShell automatically generates the following artifacts in `evidence/`:

1. `environment.json`: Node.js version, OS version, PowerShell edition, user context, timestamp.
2. `docker.json`: Docker Engine availability, Docker Compose version, container status.
3. `build.log`: Monorepo build output with **automatic secret redaction**.
4. `tests.log`: Full vitest suite execution output with **automatic secret redaction**.
5. `benchmark.log`: Benchmark runner execution and defect inspection logs.
6. `playwright.json`: Playwright configuration and Edge channel status.
7. `browser.json`: Resolved browser engine (`SYSTEM_EDGE`), path, and version (`155.0.4283.45`).
8. `git-status.json`: Working tree status and current commit SHA.
9. `result.json`: Canonical result manifest signed by the execution pipeline.

### Canonical `result.json` Schema
```json
{
  "executionMode": "HUMAN_OPERATOR_EXECUTION",
  "plannedBy": "ANTIGRAVITY",

```

## 4. Verification Lifecycle

A manual run progresses through deterministic states:

- **`MANUAL_EXECUTION_REQUIRED`**: The bundle has been planned and generated by the agent, but `RUN.ps1` has not yet been executed by the human operator.
- **`MISSING_EVIDENCE`**: `RUN.ps1` was executed, but one or more mandatory evidence files are missing from `evidence/`.
- **`FAILED`**: `result.json` reports a non-zero exit code or build/test failure.
- **`VERIFIED`**: All mandatory evidence files exist, secret redaction is intact, and exit code is 0.

> **Key Rule:** Human operator execution does not invalidate automated verification. The agent inspects the emitted evidence cryptographically and structurally, and marks `verifiedBy: "ALPER_DESIGN_OS"`.

## 5. Browser Runtime Fallback Resolver

Corporate security policies often block direct downloads of binaries (e.g. Playwright managed Chromium download blocked by network perimeter / endpoint rule). 

The Alper Design OS browser resolver executes the following deterministic chain:

```
Managed Chromium (Blocked by Policy)
         │
         ▼
System Microsoft Edge (Available: 155.0.4283.45, Channel: msedge)
         │
         ▼
System Google Chrome (Available: C:\Program Files\Google\Chrome\...)
         │
         ▼
UNAVAILABLE
```

## 6. Separated Capability vs Execution Authority in Doctor

`npm run doctor` separates what the workstation is physically capable of from what the agent's current process context is allowed to spawn:

```text
Docker Capability ........ AVAILABLE
Docker Agent Execution ... RESTRICTED
Docker Human Execution ... AVAILABLE

Browser Capability ....... AVAILABLE
Browser Agent Execution .. RESTRICTED
Browser Human Execution .. AVAILABLE

Browser Engine ........... SYSTEM_EDGE (155.0.4283.45)
Playwright Channel ....... msedge

Recommended Mode ......... HUMAN_OPERATOR_EXECUTION
```

---

## 7. Strict Security & Compliance Guardrails

Under no circumstances does Alper Design OS:
- Bypass or tamper with Xcitium or antivirus software.
- Attempt privilege escalation (e.g. UAC bypass or admin elevation).
- Disable endpoint security services.
- Alter corporate Group Policy or registry execution policies.

Execution authority remains transparently with the human developer in their own interactive shell.
